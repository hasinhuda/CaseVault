What was built, what was run, what the recorded output means, and what it does not prove. Everything below that says "run" was run on 2026-11-13 on one Windows 11 machine with Docker Desktop (Docker 29.8.0, Compose 5.5.1), compose project `casevault-rebuild`. Raw (scrubbed) output is in [docs/evidence/deploy/](../evidence/deploy/); the stack is started and checked by the scripts in `scripts/`. Anything not run is marked **NOT VERIFIED**.

## 3. The three checks from the Phase 12A review

**B7a - database password through a real secret file, including a trailing newline.** `scripts\deploy-init.ps1` writes `db_password.txt` as 32 characters plus one line feed (33 bytes). `07-secret-file.txt` shows the same 33 bytes mounted in `cvr-app` (`byte 33 = 0a`) and in `cvr-db`. The database was initialised from that file (`POSTGRES_PASSWORD_FILE`), the application authenticated with `/run/secrets/spring.datasource.password` and applied the Flyway migrations, and the container reports healthy. So the trailing line feed did **not** cause a login failure: both readers handle it (the PostgreSQL image reads the file with shell command substitution, which drops trailing newlines; Spring Boot's configtree import trims a trailing newline; the observable proof is the successful authentication). No change to the script or to the check was needed. Not tested: a CRLF-terminated file (the script never produces one).

**B7b - HSTS through nginx.** `04-headers.txt` shows exactly one `Strict-Transport-Security: max-age=31536000 ; includeSubDomains` header on the HTTPS response. It is written by the application, which treats the request as secure because nginx sends `X-Forwarded-Proto: https` and the application honours it (Phase 12A, `server.forward-headers-strategy=native`); the same header makes redirects use `https://localhost:8443/...` (`06-login.txt` shows the login redirect to `https://localhost:8443/dashboard`) and keeps the session cookie `Secure`. nginx adds no header of its own, so nothing is duplicated. Not re-demonstrated here: what happens without the forwarded protocol header (covered by the Phase 12A tests, not by this stack).

**B7c - first run, then restart without the override.** `scripts\deploy-up.ps1 -FirstRun` starts the stack with `deploy/compose.first-run.yaml`, which sets `CASEVAULT_BOOTSTRAP_INITIAL_ACCOUNTS_ENABLED=true` and the credentials file path (the application requires the path on every start while the flag is on). `scripts\deploy-up.ps1 -FinishFirstRun` recreates `cvr-app` from the base file only and deletes the credentials file. `09-first-run-finish.txt` records: the file was present before, the flag is absent from the container environment after, the `cvr_firstrun` volume is not mounted after and holds 0 files, the application is healthy, and `admin_auditor` and `client_charlie` still log in (redirect to `/dashboard`, dashboard 200) after the restart. No first-run password appears in the logs of the three containers before or after (counts 0). The accounts persist because they live in the database volume.

## 4. Findings made while building this stack

- **F-017**: the prod-like profile could never start against PostgreSQL. The base `application.properties` sets the H2 driver and the profile did not override it, so the first real start failed with "Driver org.h2.Driver claims to not accept jdbcUrl". All earlier tests replaced the datasource with H2. Fixed in `application-prod-like.properties`, guarded by DEPLOY-SECRET-05.
- **F-018**: a Windows checkout has CRLF line endings in `mvnw`, so `docker build` failed with exit code 127. The Dockerfile now normalises the script. CI (Linux) was not affected.
- `docker compose down -v` with only the base file left the `cvr_firstrun` volume (only the override references it); `deploy-down.ps1 -RemoveData` now includes the override.

## 5. Residual risk and what was not verified

1. **Self-signed certificate** (no CA, not for public use); the first browser visit shows a warning. No browser was used: **NOT VERIFIED** in Chrome or Edge.
2. **Single node, single host**: no replication, no failover; session registry and rate limiter in memory; a restart ends all sessions.
3. **Cleartext keyset and audit key** in the volume `cvr_keys`, same trust domain as the data; the database owner role can drop the audit immutability trigger.
4. **No backup, restore or rollback** was designed or demonstrated: `cvr_pgdata`, `cvr_evidence` and `cvr_keys` must be backed up together or evidence cannot be decrypted. **NOT DONE.**
5. **No image scan was run** on `cvr-app:dev`, `postgres:16-alpine` or `nginx:stable-alpine` in this phase (CI scans the application image; Trivy is not run on the compose images): **NOT VERIFIED**. Hadolint was not run locally either (CI runs it on the Dockerfile).
6. **Access logs**: nginx writes request lines (method, URL, status, address) to the container log; no bodies and no passwords were found in the logs (count 0 for the first-run passwords), but a general log-review process does not exist.
7. **Docker Desktop specifics**: secret files appear world-readable inside the container; published port bound to `127.0.0.1` on purpose. Behaviour on a Linux host or in a cloud platform is **NOT VERIFIED**.
8. **Load and failure behaviour** (memory pressure at the 640 MiB limit, nginx error pages for an unavailable application, restart policy) were not tested.
9. The opt-in for initial accounts creates the four synthetic standard accounts with no password change feature; delete the credentials file after the first login (done by `-FinishFirstRun`) and treat the passwords as long-lived.

## 6. After the first login: required steps
